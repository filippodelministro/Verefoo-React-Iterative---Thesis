\section{Implementation}

The iterative variant is implemented by modifying \texttt{VerefooSerializer}, the class that serves as the entry point to the VEREFOO tool: all invocations — vanilla, React, and now iterative — start here. Rather than passing the full set of new requirements to React-VEREFOO in a single call, the modified constructor wraps the React-VEREFOO invocation in a loop that introduces one NSR at a time. The vanilla constructor, also defined in \texttt{VerefooSerializer}, is left untouched, as are all downstream components — \texttt{VerefooProxy}, the MaxSMT encoding, and the \texttt{Translator}.

\subsection{Entry Point and initialization}

Since the iterative variant modifies the React-VEREFOO constructor, it shares the same parameters: \texttt{root} is the input \texttt{NFV} object containing the network topology and the full NSR set, \texttt{algo} selects the algorithm variant (\texttt{"AP"} for Atomic Predicates or \texttt{"MF"} for MaxFlow)\footnote{In this thesis, only the Atomic Predicates algorithm is used, as React-VEREFOO supports only the \texttt{AP} variant.}, and \texttt{react} is the boolean flag that activates the React-VEREFOO reconfiguration.

The constructor begins by building the Allocation Graph from the input Service Graph, exactly as the other two variants do:

\begin{lstlisting}[language=Java, caption={Allocation graph construction.}, label={lst:iterative-init}]
AllocationGraphGenerator agg = new AllocationGraphGenerator(root, react);
root = agg.getAllocationGraph();
\end{lstlisting}

% \subsection{Initialization}

Before the iterative loop starts, two data structures are initialized: \texttt{consideredProps} and \texttt{currentGraph}. \texttt{consideredProps} holds the requirements that have already been enforced and which will be passed as the \textit{initial} set to React-VEREFOO at each step, while \texttt{currentGraph} holds the current state of the network graph, which is updated after every successful solver invocation.

\begin{lstlisting}[language=Java, caption={Initialization of the iterative state.}, label={lst:iterative-state-init}]
List<Property> consideredProps = new ArrayList<>();
if (initialProp != null) {
    consideredProps.addAll(initialProp);
}
Graph currentGraph = g;
\end{lstlisting}

If the input \texttt{NFV} object contains a pre-existing set of already enforced requirements (\texttt{initialProp}), they are loaded into \texttt{consideredProps} at the start. This supports the general case in which the network already has a valid configuration before the first new NSR is introduced, corresponding to $P_0 \neq \emptyset$ in the algorithm description of Chapter~\ref{chap:iterative}.

\subsection{Core change:  the Iterative Loop}
\label{sec:iterative-loop}

The main loop iterates over \texttt{prop}, the list of new requirements (NSRs) to incorporate. At each step, \texttt{VerefooProxy} expects two NSR lists: \texttt{consideredProps} as the initial set of requirements already enforced, and \texttt{singleProp} as the new property to be added\footnote{\texttt{singleProp} is built as shown in Listing~\ref{lst:iterative-loop} to match the input format expected by the \texttt{VerefooProxy} interface.}. \texttt{VerefooProxy} then computes the difference between the two lists to derive the \textit{added}, \textit{kept}, and \textit{deleted} requirement sets, as described in Chapter~\ref{chap:background}. By construction, $R_a$ (the \textit{added} set) always contains exactly one element.

\begin{lstlisting}[language=Java, caption={Core of the iterative loop.}, label={lst:iterative-loop}]
for (Property currentProp : prop) {
    List<Property> singleProp = new ArrayList<>();
    singleProp.add(currentProp);
    singleProp.addAll(consideredProps);

    VerefooProxy test = new VerefooProxy(
        currentGraph,
        root.getHosts(),
        root.getConnections(),
        root.getConstraints(),
        consideredProps,   // initial set (already enforced)
        singleProp,        // new property to be enforced
        paths,
        AlgoUsed
    );
    ...
}
\end{lstlisting}

If the solver returns UNSAT, the loop does not break immediately, but instead the current \texttt{root} is kept as the result and the failure is recorded and surfaced to the caller after the loop completes.

\subsection{Summary of Changes}

In summary, the core change to the original React-VEREFOO is the introduction of the iterative loop: instead of passing the full set of new requirements to React-VEREFOO in a single call, the execution is broken in multiple intermediate steps, each adding exactly one requirement at a time. Between steps, the graph and the set of enforced requirements are updated, so that each React-VEREFOO invocation builds on a valid and already verified configuration. All other components — \texttt{VerefooProxy}, the MaxSMT encoding, the \texttt{Translator} — remain unchanged.


\section{Testing}

\subsection{Qualitative Validation on CESNET}
\label{sec:cesnet-validation}

To validate the correctness of the iterative algorithm on a realistic topology, this section traces its execution step by step on the CESNET network — the Czech academic and research backbone shown in Figure~\ref{fig:cesnet-topology}. The test is qualitative: NSRs and an initial firewall configuration are defined on the CESNET real topology, and each iteration of the algorithm is applied by hand to verify that (i) each new requirement is satisfied, and (ii) no previously satisfied requirement is broken. This mirrors the structure of the Worked Example in Chapter~\ref{chap:iterative}, applied to a real-world topology.

\subsubsection{Topology}

The topology used for this testing case is the backbone of CESNET, the Czech National Research and Education Network, shown in Figure~\ref{fig:cesnet-topology}. As modeled here it consists of 23 nodes and 28 links connecting the country's main cities and research sites. Link capacities go from 10~Mbit/s to 10~Gbit/s, reflecting a two-tier structure: a small set of high-capacity backbone links between major cities and lower-capacity links reaching smaller, peripheral sites. Praha acts as the central node having six direct neighbors; every other node is reached through one or more intermediate hops, and some destinations are reachable through more than one path.

\subsubsection{Incremental Additions}

From this point on, every step is driven by Iterative React-VEREFOO logic (Chapter~\ref{chap:background}): Step 1 classifies each new NSR as a reachability or an isolation requirement. Step 2 then differs between the two requirement types: for a reachability requirement, it checks whether some flow already reaches the destination — if so, no further action is needed; otherwise, every node currently blocking that flow becomes eligible for reconfiguration. For an isolation requirement, it checks whether the flow is already blocked — if not, every node on the path becomes a candidate for reconfiguration. Step 3 then solves a MaxSMT problem restricted to the flagged candidates eligible for reconfiguration, reusing existing firewalls and rules wherever possible.

\subsubsection{Discussion}


The clearest takeaway, already visible in $P_0$, is that the \emph{type} of NSR — reachability or isolation — is what really drives the outcome of the algorithm: the two types make it iterate in completely different ways. An unguarded Allocation Place filters nothing, so a reachability requirement can only ever find its path already open (as in iteration 5) or already blocked by an existing firewall (reconfiguration in iteration 3), but will never justify allocating a new firewall. An isolation requirement, instead, can force a genuinely new allocation, since something must start blocking traffic where nothing did before (iterations 1 and 2); but it can just as well find every path already closed by firewalls allocated for earlier requirements, needing no change at all (iteration 4). This asymmetry — reachability at most reconfiguring an existing firewall, isolation possibly allocating a new one — is itself a consequence of the \textit{whitelisting} mode chosen for this testing case (Chapter~\ref{chap:background}).

Iterations 1 and 2 both allocate a new firewall for an isolation requirement, but for structurally different reasons. In iteration 1 the two candidates have different cost — one is free, the other would break an existing reachability requirement — so the cheaper option is the clear choice. In iteration 2 the two candidates are perfectly symmetric: neither Tabor nor Pardubice appears anywhere else in the NSR set, so both cost exactly one default DROP rule. This is a true tie, and the specific choice made here — $\mathit{AP}(\text{Praha},\text{Pardubice})$ over $\mathit{AP}(\text{Praha},\text{Tabor})$ — turns out to matter later: it is precisely what leaves $\mathit{AP}(\text{Praha},\text{Tabor})$ open for iteration 5 to exploit at zero cost. Section~\ref{sec:tie-breaking-closer-look} explores this dependency in detail, showing how the choice could potentially affect subsequent iterations.

The final count — six firewalls enforcing all fifteen requested NSRs, with $p_5$, $p_6$, and $p_{15}$ still enforced by no firewall at all — illustrates that VEREFOO's optimality objective keeps the configuration compact by allocating only where traffic must actually be blocked, and that this compactness persists even as new isolation requirements are introduced over time. Together with the step-by-step verification carried out at each iteration, this confirms that the requirements introduced during the incremental phase were correctly enforced, without disrupting anything already in place.

\subsection{A Closer Look: Tie-Breaking and Flow Analysis}
\label{sec:tie-breaking-closer-look}

\paragraph{Introduction.}

This section studies one specific case from the test example above to illustrate a real dynamic that is worth considering for future work on the topic. When React-VEREFOO must allocate a new firewall to satisfy a requirement, two or more Allocation Places can turn out to be equally costly. In such cases, choosing one AP over another has no immediate impact on the cost of satisfying the current requirement, but, as shown below, it can still affect how future iterations play out. This suggests that future implementations of the tool could take traffic flow analysis into account, in order to decide which NSR to enforce first and obtain the satisfaction of later NSRs at lower cost.


\paragraph{The case.}
% todo: riportare figura nel dettaglio di entrambe le opzioni disponibili per dare contesto
Iteration 2's tie between $\mathit{AP}(\text{Praha},\text{Tabor})$ and $\mathit{AP}(\text{Praha},\text{Pardubice})$ is worth revisiting in detail, because the two resolutions lead to visibly different outcomes especially for iteration 5. The two options are equivalent in terms of cost for $p_{12}$, but they differ in how they affect the reachability of Tabor $\to$ Usti n.L. when $p_{15}$ is later introduced. The two cases are summarized below.

\paragraph{Case (a): the firewall is placed at $\mathit{AP}(\text{Praha},\text{Pardubice})$.} This is the resolution followed by the main trace above. $\mathit{AP}(\text{Praha},\text{Tabor})$ is left untouched, and when $p_{15}$ (Tabor $\to$ Usti n.L.) is introduced in iteration 5, its entire path is already open: the requirement is satisfied at zero cost, with no reconfiguration at all.

\paragraph{Case (b): the firewall is placed at $\mathit{AP}(\text{Praha},\text{Tabor})$ instead.} In this alternative scenario however, allocating the new firewall enforced by $p_{12}$ at $\mathit{AP}(\text{Praha},\text{Tabor})$ would block every flow originating at Tabor, including the Tabor $\to$ Usti n.L. flow that $p_{15}$ will later request to be reachable. According to this, Step 2 of iteration 5 would find the Tabor $\to$ Usti n.L. flow already blocked by this same firewall, and the only candidate for reconfiguration would be the firewall itself: React-VEREFOO would add \texttt{ALLOW Tabor $\to$ Usti n.L.} to it. The requirement would still be satisfied — correctness is unaffected either way — but through a reconfiguration rather than a free pass.

\paragraph{Discussion}

The consideration worth mentioning is that both choices are valid and correct, but one (a) achieves the result at zero cost, while the other (b) requires a reconfiguration. Although minimal in this example, this is an illustrative case of how a tie-break decision can have consequences on the cost of satisfying future NSRs. $p_{12}$ itself is satisfied at identical cost either way, and the choice between the two candidates is left to the implementation of React-VEREFOO, with no visibility into future NSRs — which is exactly why the two cases only diverge later, in $p_{15}$, a requirement that does not even exist yet at the time the tie is resolved.

This observation points to a natural extension of the approach that falls outside the scope of this thesis: a \emph{traffic-aware} strategy may be considered for future work, applied before listing the NSRs and presenting them to the iterative version of React-VEREFOO, aiming to classify NSRs by their traffic flows and order them across iterations so as to minimize the number of future reconfigurations.
