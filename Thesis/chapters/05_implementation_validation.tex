\section{Implementation}

The iterative variant is implemented by modifying \texttt{VerefooSerializer}, the class that serves as the entry point to the VEREFOO tool: all invocations — vanilla, React, and now iterative — start here. Rather than passing the full set of new requirements to React-VEREFOO in a single call, the modified constructor wraps the React-VEREFOO invocation in a loop that introduces one NSR at a time. The vanilla constructor, also defined in \texttt{VerefooSerializer}, is left untouched, as are all downstream components — \texttt{VerefooProxy}, the MaxSMT encoding, and the \texttt{Translator}.

\subsection{Entry Point and initialization}

Since the iterative variant modifies the React-VEREFOO constructor, it shares the same parameters: \texttt{root} is the input \texttt{NFV} object containing the network topology and the full NSR set, \texttt{algo} selects the algorithm variant (\texttt{"AP"} for Atomic Predicates or \texttt{"MF"} for MaxFlow)\footnote{In this thesis, only the Atomic Predicates algorithm is used, as React-VEREFOO supports only the \texttt{AP} variant.}, and \texttt{react} is the boolean flag that activates the React-VEREFOO reconfiguration.

The constructor begins by building the Allocation Graph from the input Service Graph, exactly as the other two variants do:

\begin{lstlisting}[language=Java, caption={Allocation graph construction.}, label={lst:iterative-init}]
AllocationGraphGenerator agg = new AllocationGraphGenerator(root, react);
root = agg.getAllocationGraph();
\end{lstlisting}

% \subsection{Initialization}

Before the iterative loop starts, two data structures are initialized: \texttt{consideredProps} and \texttt{currentGraph}. \texttt{consideredProps} holds the requirements that have already been enforced and which will be passed as the \textit{initial} set to React-VEREFOO at each step, while \texttt{currentGraph} holds the current state of the network graph, which is updated after every successful solver invocation.

\begin{lstlisting}[language=Java, caption={Initialization of the iterative state.}, label={lst:iterative-state-init}]
List<Property> consideredProps = new ArrayList<>();
if (initialProp != null) {
    consideredProps.addAll(initialProp);
}
Graph currentGraph = g;
\end{lstlisting}

If the input \texttt{NFV} object contains a pre-existing set of already enforced requirements (\texttt{initialProp}), they are loaded into \texttt{consideredProps} at the start. This supports the general case in which the network already has a valid configuration before the first new NSR is introduced, corresponding to $P_0 \neq \emptyset$ in the algorithm description of Chapter~\ref{chap:iterative}.

\subsection{Core change:  the Iterative Loop}

The main loop iterates over \texttt{prop}, the list of new requirements (NSRs) to incorporate. At each step, \texttt{VerefooProxy} is expects two NSR lists: \texttt{consideredProps} as the initial set of requirements already enforced, and \texttt{singleProp} as the new property to be added\footnote{\texttt{singleProp} is built as shown in Listing~\ref{lst:iterative-loop} to match the input format expected by the \texttt{VerefooProxy} interface.}. \texttt{VerefooProxy} then computes the difference between the two lists to derive the \textit{added}, \textit{kept}, and \textit{deleted} requirement sets, as described in Chapter~\ref{chap:background}. By construction, $R_a$ (the \textit{added} set) always contains exactly one element.

\begin{lstlisting}[language=Java, caption={Core of the iterative loop.}, label={lst:iterative-loop}]
for (Property currentProp : prop) {
    List<Property> singleProp = new ArrayList<>();
    singleProp.add(currentProp);
    singleProp.addAll(consideredProps);

    VerefooProxy test = new VerefooProxy(
        currentGraph,
        root.getHosts(),
        root.getConnections(),
        root.getConstraints(),
        consideredProps,   // initial set (already enforced)
        singleProp,        // new property to be enforced
        paths,
        AlgoUsed
    );
    ...
}
\end{lstlisting}

After each \texttt{VerefooProxy} call, the result is examined. If all the requirements are satisfied, the current requirement is added to \texttt{consideredProps} and \texttt{currentGraph} is updated to the graph produced by the solver, so that the intermediate result is propagated to the next iteration. If the solver returns UNSAT, the loop does not break immediately, but instead the current \texttt{root} is kept as the result and the failure is recorded and surfaced to the caller after the loop completes.

\subsection{Summary of Changes}

In summary, the core changes to the original React-VEREFOO is the introduction of the iterative loop: instead of passing the full set of new requirements to React-VEREFOO in a single call, the execution is broken in multiple intermediate steps, each adding exactly one requirement at a time. Between steps, the graph and the set of enforced requirements are updated, so that each React-VEREFOO invocation builds on a valid and already verified configuration. All other components — \texttt{VerefooProxy}, the MaxSMT encoding, the \texttt{Translator} — remain unchaged.


\section{Testing}

\subsection{Qualitative Validation on CESNET}
\label{sec:cesnet-validation}

To validate the correctness of the iterative algorithm on a realistic topology, this section traces its execution step by step on the CESNET network — the Czech academic and research backbone shown in Figure~\ref{fig:cesnet-topology}. The trace is qualitative: NSRs and an initial firewall configuration are defined on the CESNET real topology, and each iteration of the algorithm is applied by hand to verify that (i) each new requirement is satisfied, and (ii) no previously satisfied requirement is broken. This mirrors the structure of the Worked Example in Chapter~\ref{chap:iterative}, applied to a real-world topology.

\subsubsection{Topology}

The topology used for this trace is the backbone of CESNET, the Czech National Research and Education Network, shown in Figure~\ref{fig:cesnet-topology}. As modeled here it consists of 23 nodes and 28 links connecting the country's main cities and research sites. Link capacities goes from 10~Mbit/s to 10~Gbit/s, reflecting a two-tier structure: a small set of high-capacity backbone links between major cities and lower-capacity links reaching smaller, peripheral sites. Praha acts as the central node having six direct neighbors; every other node is reached through one or more intermediate hops, and some destinations are reachable through more than one path.

\subsubsection{Initial Configuration ($P_0$)}
This is a plausible test case constructed to exercise the iterative implementation, not an actual CESNET deployment: node names and the physical topology (links and capacities) are taken from the real network, but the reachability and isolation requirements are defined for this evaluation and do not reflect any real security policy in use on CESNET.

Ten initial NSRs are defined ($P_0$). Praha requires bidirectional reachability with Brno, Plzen, and Usti n.L. ($p_1$–$p_6$). Ostrava must not be able to reach Praha, Plzen, or Usti n.L. ($p_7$–$p_9$). Brno must not be able to reach Plzen ($p_{10}$). Table~\ref{tab:cesnet-initial} lists the ten requirements.

\paragraph{Iteration 1 — $p_{11}$: Kutna Hora $\to$ Praha (Reachability).}

\begin{center}
$R_k = P_0,\quad R_a = \{p_{11}\},\quad R_d = \emptyset$
\end{center}

Kutna Hora is a direct neighbor of Praha, but $\mathit{AP}(\text{Praha},\text{Kutna Hora})$ currently hosts no firewall (plain forwarder) — nothing in $P_0$ uses this link. React-VEREFOO allocates a new firewall:

\smallskip
$\mathit{FW}$ at $\mathit{AP}(\text{Praha},\text{Kutna Hora})$:\\
\texttt{\textbf{ALLOW Kutna Hora $\to$ Praha}} \hfill ($p_{11}$, new)\\
\texttt{default: DROP}
\smallskip

No existing firewall is modified; all $P_0$ requirements remain satisfied.\\
\textbf{Result: SAT.} New firewall allocated.

\paragraph{Iteration 2 — $p_{12}$: Pardubice $\to$ Kutna Hora (Reachability).}

\begin{center}
$R_k = P_0 \cup \{p_{11}\},\quad R_a = \{p_{12}\},\quad R_d = \emptyset$
\end{center}

Pardubice and Kutna Hora are directly connected; $\mathit{AP}(\text{Kutna Hora},\text{Pardubice})$ has no firewall yet. React-VEREFOO allocates:

\smallskip
$\mathit{FW}$ at $\mathit{AP}(\text{Kutna Hora},\text{Pardubice})$:\\
\texttt{\textbf{ALLOW Pardubice $\to$ Kutna Hora}} \hfill ($p_{12}$, new)\\
\texttt{default: DROP}
\smallskip

This does not interact with any $P_0$ requirement: Pardubice and Kutna Hora were previously disconnected from every NSR in the trace.\\
\textbf{Result: SAT.} New firewall allocated.

\paragraph{Iteration 3 — $p_{13}$: Pardubice $\to$ Praha (Reachability).}

\begin{center}
$R_k = P_0 \cup \{p_{11},p_{12}\},\quad R_a = \{p_{13}\},\quad R_d = \emptyset$
\end{center}

Traffic Pardubice $\to$ Praha follows the path \texttt{Pardubice–Kutna Hora–Praha}, crossing two existing firewalls in sequence. Neither currently has a rule for the Pardubice$\to$Praha traffic class (each only allows the single-hop class it was configured for in the previous two iterations). React-VEREFOO reconfigures both simultaneously:

\smallskip
$\mathit{FW}$ at $\mathit{AP}(\text{Kutna Hora},\text{Pardubice})$ updated:\\
\texttt{ALLOW Pardubice $\to$ Kutna Hora} \hfill ($p_{12}$)\\
\texttt{\textbf{ALLOW Pardubice $\to$ Praha}} \hfill ($p_{13}$, new — transit class)\\
\texttt{default: DROP}

\medskip
$\mathit{FW}$ at $\mathit{AP}(\text{Praha},\text{Kutna Hora})$ updated:\\
\texttt{ALLOW Kutna Hora $\to$ Praha} \hfill ($p_{11}$)\\
\texttt{\textbf{ALLOW Pardubice $\to$ Praha}} \hfill ($p_{13}$, new)\\
\texttt{default: DROP}
\smallskip

This new route does not touch Ostrava (still confined behind its two blocked egress links) or Brno, so $p_7$–$p_{10}$ are unaffected.\\
\textbf{Result: SAT.} Two firewalls reconfigured.

\paragraph{Iteration 4 — $p_{14}$: Mar.Lazne $\to$ Ostrava (Isolation).}

\begin{center}
$R_k = P_0 \cup \{p_{11},p_{12},p_{13}\},\quad R_a = \{p_{14}\},\quad R_d = \emptyset$
\end{center}

Any path from Mar.Lazne toward Ostrava must eventually cross $\mathit{AP}(\text{Opava},\text{Ostrava})$ or $\mathit{AP}(\text{Olomouc},\text{Ostrava})$ — the only two links entering Ostrava in the entire network. Both already default to DROP with no ALLOW rule for any origin. The requirement is therefore already satisfied, regardless of the route Mar.Lazne-originated traffic takes through the backbone.\\
\textbf{Result: SAT, no change.}

\begin{center}

Traffic Cheb $\to$ Plzen follows the path \texttt{Cheb–Mar.Lazne–Plzen}, crossing $\mathit{FW}_2$ at $\mathit{AP}(\text{Mar.Lazne},\text{Plzen})$. $\mathit{FW}_2$ currently allows only the Praha$\to$Plzen traffic class; Cheb-originated traffic destined for Plzen has no matching rule and is dropped. \smallskip
$\mathit{FW}_2$ updated ($\mathit{AP}(\text{Mar.Lazne},\text{Plzen})$):\\
\texttt{ALLOW Praha $\to$ Plzen} \hfill ($p_3$)\\
\texttt{ALLOW Plzen $\to$ Praha} \hfill ($p_4$)\\

\textbf{Result: SAT.} $\mathit{FW}_2$ reconfigured.

\subsubsection{Discussion}

The trace exhibits all three outcomes the iterative algorithm can produce for a single new NSR: allocating a new firewall on a previously uncontrolled link (iterations 1 and 2), reconfiguring one or more existing firewalls that already sit on the relevant path (iterations 3 and 5), and detecting that the current configuration already satisfies the requirement with no modification at all (iteration 4). Iteration 3 additionally shows that a single new NSR can require the \emph{simultaneous} reconfiguration of two firewalls along a multi-hop path, which React-VEREFOO resolves in one solver call rather than one call per affected link.

The final count — eight firewalls for fifteen NSRs — also illustrates that placing firewalls at natural bottlenecks (Ostrava's two egress links, rather than every downstream convergence point) keeps the configuration compact even as the requirement set grows.

More importantly, the verification table demonstrates the key correctness property: \emph{monotonic consistency}. Because each React-VEREFOO invocation receives the full set of already-enforced requirements as its initial state ($R_k$), the solver is constrained to produce a configuration that satisfies both old and new requirements simultaneously. No requirement satisfied at step $i$ can be violated at step $i+1$. This follows by induction: the base case ($P_0$ correctly enforced before the loop) holds by construction, and the inductive step is guaranteed by React-VEREFOO's correctness guarantee over $R_k$.
