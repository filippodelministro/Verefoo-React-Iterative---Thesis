\section{Implementation}

The iterative variant is implemented by modifying \texttt{VerefooSerializer}, the class that serves as the entry point to the VEREFOO tool: all invocations — vanilla, React, and now iterative — start here. Rather than passing the full set of new requirements to React-VEREFOO in a single call, the modified constructor wraps the React-VEREFOO invocation in a loop that introduces one NSR at a time. The vanilla constructor, also defined in \texttt{VerefooSerializer}, is left untouched, as are all downstream components — \texttt{VerefooProxy}, the MaxSMT encoding, and the \texttt{Translator}.

\subsection{Entry Point and initialization}

Since the iterative variant modifies the React-VEREFOO constructor, it shares the same parameters: \texttt{root} is the input \texttt{NFV} object containing the network topology and the full NSR set, \texttt{algo} selects the algorithm variant (\texttt{"AP"} for Atomic Predicates or \texttt{"MF"} for MaxFlow)\footnote{In this thesis, only the Atomic Predicates algorithm is used, as React-VEREFOO supports only the \texttt{AP} variant.}, and \texttt{react} is the boolean flag that activates the React-VEREFOO reconfiguration.

The constructor begins by building the Allocation Graph from the input Service Graph, exactly as the other two variants do:

\begin{lstlisting}[language=Java, caption={Allocation graph construction.}, label={lst:iterative-init}]
AllocationGraphGenerator agg = new AllocationGraphGenerator(root, react);
root = agg.getAllocationGraph();
\end{lstlisting}

% \subsection{Initialization}

Before the iterative loop starts, two data structures are initialized: \texttt{consideredProps} and \texttt{currentGraph}. \texttt{consideredProps} holds the requirements that have already been enforced and which will be passed as the \textit{initial} set to React-VEREFOO at each step, while \texttt{currentGraph} holds the current state of the network graph, which is updated after every successful solver invocation.

\begin{lstlisting}[language=Java, caption={Initialization of the iterative state.}, label={lst:iterative-state-init}]
List<Property> consideredProps = new ArrayList<>();
if (initialProp != null) {
    consideredProps.addAll(initialProp);
}
Graph currentGraph = g;
\end{lstlisting}

If the input \texttt{NFV} object contains a pre-existing set of already enforced requirements (\texttt{initialProp}), they are loaded into \texttt{consideredProps} at the start. This supports the general case in which the network already has a valid configuration before the first new NSR is introduced, corresponding to $P_0 \neq \emptyset$ in the algorithm description of Chapter~\ref{chap:iterative}.

\subsection{Core change:  the Iterative Loop}
\label{sec:iterative-loop}

The main loop iterates over \texttt{prop}, the list of new requirements (NSRs) to incorporate. At each step, \texttt{VerefooProxy} expects two NSR lists: \texttt{consideredProps} as the initial set of requirements already enforced, and \texttt{singleProp} as the new property to be added\footnote{\texttt{singleProp} is built as shown in Listing~\ref{lst:iterative-loop} to match the input format expected by the \texttt{VerefooProxy} interface.}. \texttt{VerefooProxy} then computes the difference between the two lists to derive the \textit{added}, \textit{kept}, and \textit{deleted} requirement sets, as described in Chapter~\ref{chap:background}. By construction, $R_a$ (the \textit{added} set) always contains exactly one element.

\begin{lstlisting}[language=Java, caption={Core of the iterative loop.}, label={lst:iterative-loop}]
for (Property currentProp : prop) {
    List<Property> singleProp = new ArrayList<>();
    singleProp.add(currentProp);
    singleProp.addAll(consideredProps);

    VerefooProxy test = new VerefooProxy(
        currentGraph,
        root.getHosts(),
        root.getConnections(),
        root.getConstraints(),
        consideredProps,   // initial set (already enforced)
        singleProp,        // new property to be enforced
        paths,
        AlgoUsed
    );
    ...
}
\end{lstlisting}

% \subsection{State Update}

After each \texttt{VerefooProxy} call, the result is examined. If all the requirements are satisfied, the current requirement is added to \texttt{consideredProps} and \texttt{currentGraph} is updated to the graph produced by the solver, so that the intermediate result is propagated to the next iteration. If the solver returns UNSAT, the loop does not break immediately, but instead the current \texttt{root} is kept as the result and the failure is recorded and surfaced to the caller after the loop completes.

\subsection{Summary of Changes}

In summary, the core change to the original React-VEREFOO is the introduction of the iterative loop: instead of passing the full set of new requirements to React-VEREFOO in a single call, the execution is broken in multiple intermediate steps, each adding exactly one requirement at a time. Between steps, the graph and the set of enforced requirements are updated, so that each React-VEREFOO invocation builds on a valid and already verified configuration. All other components — \texttt{VerefooProxy}, the MaxSMT encoding, the \texttt{Translator} — remain unchanged.

\subsection{Qualitative Validation on CESNET}
\label{sec:cesnet-validation}

To validate the correctness of the iterative algorithm on a realistic topology, this section traces its execution step by step on the CESNET network — the Czech academic and research backbone shown in Figure~\ref{fig:cesnet-topology}. The test is qualitative: NSRs and an initial firewall configuration are defined on the CESNET real topology, and each iteration of the algorithm is applied by hand to verify that (i) each new requirement is satisfied, and (ii) no previously satisfied requirement is broken. This mirrors the structure of the Worked Example in Chapter~\ref{chap:iterative}, applied to a real-world topology.

\subsubsection{Topology}

The topology used for this testing case is the backbone of CESNET, the Czech National Research and Education Network, shown in Figure~\ref{fig:cesnet-topology}. As modeled here it consists of 23 nodes and 28 links connecting the country's main cities and research sites. Link capacities go from 10~Mbit/s to 10~Gbit/s, reflecting a two-tier structure: a small set of high-capacity backbone links between major cities and lower-capacity links reaching smaller, peripheral sites. Praha acts as the central node having six direct neighbors; every other node is reached through one or more intermediate hops, and some destinations are reachable through more than one path.

\subsubsection{Incremental Additions}

From this point on, every step is driven by Iterative React-VEREFOO logic (Chapter~\ref{chap:background}): Step 1 classifies each new NSR as a reachability or an isolation requirement. Step 2 then differs between the two requirement types: for a reachability requirement, it checks whether some flow already reaches the destination — if so, no further action is needed; otherwise, every node currently blocking that flow becomes eligible for reconfiguration. For an isolation requirement, it checks whether the flow is already blocked — if not, every node on the path becomes a candidate for reconfiguration. Step 3 then solves a MaxSMT problem restricted to the flagged candidates eligible for reconfiguration, reusing existing firewalls and rules wherever possible.

\subsubsection{Discussion}

The clearest takeaway, already visible in $P_0$, is that the \emph{type} of NSR — reachability or isolation — is what really drives the outcome of the algorithm: the two types make it iterate in completely different ways. A reachability requirement can only find its path already unprotected (as in iteration 5) or already being blocked by an existing firewall (resulting in reconfiguration as in iteration 3), but will never justify allocating a new firewall. An isolation requirement, instead, can force a genuinely new allocation, to start blocking traffic where nothing did before (iterations 1 and 2); but it can also find every path already closed by firewalls allocated for earlier requirements, needing no change at all (iteration 4). This asymmetry — reachability at most reconfiguring an existing firewall, isolation possibly allocating a new one — is itself a consequence of the \textit{whitelisting} mode chosen for this testing case (Chapter~\ref{chap:background}).

Iterations 1 and 2 both allocate a new firewall for an isolation requirement, but each selects its Allocation Place for a different reason. In iteration 1 the two direct candidates have different cost — one is free, the other would break an existing reachability requirement — so the cheaper option is the clear choice. Iteration 2 looks similar at first, since Tabor and Pardubice appear nowhere else in the NSR set, but the isolation itself is reachable by two distinct routes, not only one: closing only the direct Tabor--Pardubice link leaves the longer route through Usti n.L. open. $\mathit{AP}(\text{Praha},\text{Tabor})$ is the only candidate that sits on both routes at once — since Tabor is a leaf node linked to Praha — so it closes the isolation with a single firewall, at half the cost of any alternative. Allocating a firewall on link $\mathit{AP}(\text{Praha},\text{Tabor})$ forces a reconfiguration at iteration 5 to allow traffic from Tabor to Usti n.L., as required by $p_{15}$.

The final result counts five firewalls enforcing all fifteen requested NSRs. The step-by-step verification carried out at each iteration confirms that the requirements introduced during the incremental phase were correctly enforced, without disrupting any requirement already in place.

\subsection{A Closer Look: Tie-Breaking and Flow Analysis}
\label{sec:tie-breaking-closer-look}

When React-VEREFOO must allocate a new firewall to satisfy an isolation requirement, it is not unusual for two or more Allocation Places to turn out equally costly with respect to the requirement being processed: assuming each candidate, would need the same number of new rules, there is no reason to prefer one over the other at that stage. But it may happen that this is not neutrally propagated into the following iterations. If a later NSR happens to require reachability across that same link, Step 2 of the iterative process will find it blocked by the firewall just placed, and will need to reconfigure it with a new ALLOW exception. However, in an alternative scenario where the equally-cheap candidate would have been chosen, the later requirement might have found its path still open at later iteration, and been satisfied at zero cost. Both outcomes remain correct regardless of which candidate is chosen: the difference only relies on the number of configurations rules needed, not on their validity.

This observation - taken as an example of several equally plausible scenarios taht couls arise elsewhere in the process - points to a natural extension of the approach, that falls outside the scope of this thesis: a \emph{traffic-aware} strategy may be considered for future work, applied before listing the NSRs and presenting them to the iterative version of React-VEREFOO, aiming to classify NSRs by their traffic flows and order them across iterations so as to minimize the number of future reconfigurations, or to break such ties by anticipating which candidate is less likely to be needed again later.

\subsection{Discussion and Limitations}
\label{sec:discussion-limitations}

\paragraph{A monolithic benchmark.} To put the iterative result in context, vanilla VEREFOO was also run once, monolithically, on the very same CESNET topology and the complete set of fifteen NSRs — the ten of $P_0$ together with the five introduced across the incremental phase — handed to the solver all at once instead of one at a time. The topology was modeled with the same conventions used throughout this validation: every router is a fixed forwarder, and each of the 28 links carries its own dedicated Allocation Place, exactly as in the iterative trace. This ensures the comparison only refers to \emph{when} the solver sees the requirements, whether all at once or one at a time.

The monolithic run is SAT, and it satisfies all fifteen requirements with five firewalls, exactly as many as the iterative trace. Table~\ref{tab:cesnet-monolithic} summarizes the result.

Three of the five firewalls match exactly between the two configurations, each pair sitting on the same Allocation Place and playing the same role: $\mathit{FW}^{M}_1$ acts exactly as $\mathit{FW}_2$ does in the iterative version, at $\mathit{AP}(\text{Praha},\text{Brno})$; $\mathit{FW}^{M}_2$ as $\mathit{FW}_4$, at $\mathit{AP}(\text{Praha},\text{Podebrady})$; and $\mathit{FW}^{M}_5$ as $\mathit{FW}_3$, at $\mathit{AP}(\text{C.Budejovice},\text{Plzen})$. The remaining two placements differ, and the difference traces back to a single decision: where to enforce Ostrava and Olomouc's northern isolation ($p_7$--$p_9$, $p_{14}$). The iterative solution commits to this by placing $\mathit{FW}_1$ in $\mathit{AP}(\text{Hradec Kralove},\text{Letohrad})$ already in $P_0$, long before $p_{12}$ or $p_{13}$ exist. The monolithic run, seeing the full set of fifteen NSRs at once, instead places a firewall at $\mathit{AP}(\text{Usti n.L.},\text{Liberec})$ — a different point on the very same path (Opava--Letohrad--Hradec Kralove--Liberec--Usti n.L.). This is not an equivalent choice: $\mathit{AP}(\text{Usti n.L.},\text{Liberec})$ also happens to sit on Tabor's alternate route to Pardubice (Tabor--Praha--Usti n.L.--Liberec--Hradec Kralove--Pardubice), so placing the isolation firewall there closes that route too, at no extra cost. This is why the monolithic solution only needs one more firewall, at $\mathit{AP}(\text{Praha},\text{Pardubice})$, to close $p_{12}$'s direct route, and never needs a firewall dedicated to Tabor at all. The iterative trace, having already committed $\mathit{FW}_1$ to Hradec Kralove--Letohrad in $P_0$, cannot retroactively move it once $p_{12}$ introduces the alternate-route requirement, and must instead allocate a fifth firewall dedicated to $\mathit{AP}(\text{Praha},\text{Tabor})$ to close both of Tabor's routes at once. While the two solutions are equivalent in firewall count, the iterative solution carries one extra ALLOW rule, needed in iteration 5 to let Tabor $\to$ Usti n.L. traffic through, after it was blocked by allocating $\mathit{FW}_5$ in iteration 2.

\paragraph{Why the two configurations differ, despite the tie.} Reaching the same firewall count does not mean the two approaches reasoned the same way, and the placement gap that remains is still informative. The monolithic solver optimizes over the complete, final NSR set in a single MaxSMT call, allowing a trade off on which existing firewall to reuse against which new one to allocate: it recognizes that closing the northern route at $\mathit{AP}(\text{Usti n.L.},\text{Liberec})$ is free once that firewall is needed anyway, and that this same placement also spares it a dedicated firewall for $p_{12}$. The iterative process, by construction, only ever sees \texttt{consideredProps} — the NSRs introduced so far — and must commit to a placement without knowledge of what will be asked next; $P_0$ allocates $\mathit{FW}_1$ at $\mathit{AP}(\text{Hradec Kralove},\text{Letohrad})$ without knowing the existence of $p_{12}$, and, with it, the opportunity to close the same route more cheaply somewhere else. This costs the iterative configuration one extra exception rule compared to the monolithic one, needed to reconfigure the dedicated Tabor firewall in iteration 5 — consistent with a process that only commits to what it knows at each step, and refines it as more requirements come in.


\paragraph{Why the iterative result may still be preferable.} The comparison between the two versions is still useful despite the tie in firewall count. It is worth recalling that this validation is a qualitative test, meant to show the correctness of the iterative algorithm and to give a rough, contextual sense of how it compares to monolithic VEREFOO as a benchmark, rather than to establish a precise, general performance ranking between the two.
In a real network, policies do not materialize all at once but accumulate over time, which is precisely the assumption the iterative approach is built around; a monolithic re-run instead needs the entire final NSR set available upfront, and offers no guarantee of \emph{stability} between successive re-solves. As seen above, a different global arrangement can lead the solver to relocate the firewall enforcing $p_7$--$p_9$ from $\mathit{AP}(\text{Hradec Kralove},\text{Letohrad})$ to $\mathit{AP}(\text{Usti n.L.},\text{Liberec})$ once $p_{12}$ enters the picture, even though the original placement was still perfectly valid. Every such relocation is an additional reconfiguration with a real operational cost, even for a firewall whose behavior, from the network operator's point of view, did not need to change at all. React-VEREFOO's reuse-biased Step 2 and Step 3 avoid this by design: once a firewall is placed, it is left untouched unless the new requirement genuinely cannot be satisfied without altering it.

The other expected advantage is scalability, though this validation is too small to show it directly: with only fifteen NSRs on this topology, both approaches solve quickly, and the small scale of this qualitative test does not stress the difference. The gain is expected to matter for larger changes — bigger topologies and larger, more frequent NSR sets — where re-solving the whole configuration from scratch grows increasingly expensive compared to solving one requirement at a time against a mostly-fixed configuration. Confirming this with a timing benchmark at scale is left as future work.
